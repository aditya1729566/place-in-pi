# Search and API contract

The corpus contains decimal digits after the decimal point. Position 1 is the first `1` in `3.1415...`. Match starts are one-based, overlaps count across shards, and surrounding context is clipped to verified coverage. Only a complete search can supply `total_matches`; scan timeout returns `null` and `complete=false`.

Endpoints: `GET /api/health`, `GET /api/corpus`, `GET /api/encodings`, `POST /api/encode`, `POST /api/search`, `GET /api/digits?start=1&count=200`. Search accepts `text`, `profile_id`, `letters_only`, `limit` (1–100), and optional opaque `cursor`. Its response has `query`, `corpus`, `result`, and `execution`, including first position, positions, total, completion flags, method, and measured elapsed time. The cursor contains a pattern digest, corpus version, and result offset; the server validates those fields. A later page repeats the selected search without storing user text. The frontend transfers a home-page query to the search page through session storage; it does not put text in the URL. Search text is not logged.

The worker protocol is tab-delimited ASCII on stdin/stdout. `SCAN\t<decimal-pattern>\t<offset>\t<limit>\t<timeout-ms>` returns one tab-delimited result. `DIGITS\t<start>\t<count>` returns a bounded digit string, including windows that cross shards. A valid four-digit prefix index is preferred for patterns of length ≥4; its candidates are checked against original corpus digits. KMP scanning is the fallback. The API owns validation, worker lifecycle, and HTTP errors; the worker validates decimal patterns and bounds again.
